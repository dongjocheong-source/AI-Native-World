1
Stage 01

프롬프트 엔지니어링

AI로부터 원하는 결과를 얻기 위해 입력값(질문·지시어)을 설계하고 최적화하는 기술. 단순한 질문을 넘어 AI의 논리적 사고를 유도해 업무 효율과 답변 정확도를 극대화하는 과정.

1

페르소나 설정

AI에게 명확한 역할과 관점을 부여

2

구체적 맥락 제공

작업에 필요한 배경 정보를 함께 전달

3

출력 형식 지정

원하는 답변의 구조·형태를 명시

한계 — 질문 설계만으로는 한계점이 많음. 복잡하고 맥락 의존적인 작업에서는 별도의 정보 설계가 필요해짐.
2
Stage 02

컨텍스트 엔지니어링

배경 정보를 함께 제공해 AI가 상황을 이해하도록 돕는 기술.

정의

AI가 상황을 정확히 이해할 수 있도록 관련된 배경지식, 이전 대화 내용, 특정 제약 조건을 체계적으로 제공하는 기술. 단순히 질문을 잘 던지는 것을 넘어, AI에게 필요한 '정보의 환경'을 설계하는 과정.

제공하는 정보 요소

배경지식관련 도메인·사실 정보
이전 대화 내용대화 흐름과 히스토리
제약 조건지켜야 할 규칙과 범위

기대 효과

할루시네이션(환각 현상) 감소근거 없는 답변 생성을 줄임
사용자 의도에 부합하는 답변가장 정교하고 적합한 결과 생성 유도
품질과 일관성 향상
Anthropic의 정의: 컨텍스트 엔지니어링은 "추론 시 최적의 토큰 집합을 큐레이션하고 유지하는 전략의 집합". 프롬프트가 "어떻게 생각할지"를 알려준다면, 컨텍스트는 "무엇을 알아야 하는지"를 결정한다 — 프롬프트가 한 번의 입력이라면, 컨텍스트는 추론마다 반복되는 큐레이션 과정이다.
3
Stage 03

MCP + 스킬

MCP는 AI와 외부 데이터를 잇는 '표준화된 파이프라인', 스킬은 그 파이프라인으로 AI가 실제로 휘두르는 '전문적인 도구'.

MCPModel Context Protocol

정의

AI 모델이 로컬 데이터나 외부 도구·서비스와 안전하고 표준화된 방식으로 연결되도록 돕는 오픈 표준 인터페이스

역할

서비스마다 다른 연결 방식 대신, 하나의 공통 규격으로 DB·파일 시스템·API 등을 쉽게 읽고 쓰게 하는 '데이터의 통로'. AI 앱 M개와 데이터 소스 N개를 일일이 잇던 M×N 연동 문제를 표준 하나로 해결

2024년 11월 Anthropic이 오픈소스로 공개. 이후 OpenAI·Google DeepMind도 채택했고, 현재 1만 6천 개 이상의 MCP 서버가 공개돼 있다

+
스킬Skill

정의

AI가 특정 작업을 수행하기 위해 실행할 수 있는 구체적인 기능·도구(Tool)의 집합

역할

텍스트 생성을 넘어 "웹 검색", "이미지 생성", "이메일 전송" 같은 실제 행동을 취하게 하는 '실행 능력' 부여

모든 지식을 한 번에 넣지 않고 필요한 순간에만 불러오는 '점진적 공개(Progressive Disclosure)' 방식으로 설계하면 컨텍스트가 깨끗하게 유지된다

단점 — 스킬 수가 늘어날수록 관리 부담 증가
4
Stage 04

하네스 엔지니어링

하네스(마구) — 말을 다루는 도구. AI 에이전트가 뛰어난 개발자가 되도록 개발 환경과 안전장치를 설계하는 방식.

AI 에이전트가 안정적으로 개발 작업을 수행하도록 코드, 도구, 테스트, 규칙, 실행 환경을 설계하는 엔지니어링 방식. 단순히 AI에게 코딩을 시키는 것이 아니라, 실수 없이 반복 가능하게 일하도록 안전장치를 구축하는 것이 핵심.

Agent = Model + Harness — Terraform 창시자 Mitchell Hashimoto의 공식. 모델은 절반일 뿐, 나머지 절반은 그 모델을 둘러싼 시스템이다. "에이전트가 실수할 때마다, 그 실수가 다시는 발생하지 않도록 시스템을 엔지니어링하라."

일반 AI 모델

Text In → Text Out

이전 맥락을 기억하지 못하는 일회성 응답

하네스가 적용된 AI 에이전트

이전 메시지를 기억 → 반복 가능한 작업 수행

하네스가 이미 돌아가고 있다는 신호 = 대화 기억

목표 — 개발자의 판단력 + AI 에이전트의 실행력을 결합해 소프트웨어 개발 속도와 품질을 동시에 높이는 것

하네스 엔지니어링의 3가지 구성요소

1

컨텍스트 파일

CLAUDE.md, AGENT.md
프로젝트의 규칙과 맥락을 담아 AI가 항상 참조하는 기준 문서
2

자동 강제 시스템

린터 · 프리커밋 훅
린터(코드 맞춤법 검사)가 규칙 위반을 자동 감지하고, 프리커밋 훅이 저장 전 자동 검사 → 린터 경고 시 에이전트가 스스로 수정하는 자동 교정 루프로 사람 개입 없이 품질 유지. SessionStart·PreToolUse·PostToolUse·Stop 같은 훅이 각 단계에서 개입한다
3

서브에이전트

컨텍스트 방화벽
역할을 나누기 위해서가 아니라, 메인 에이전트의 컨텍스트가 꽉 찼을 때 세부 작업을 위임하는 용도. 독립된 컨텍스트에서 작업하고 결과만 돌려줘 중간 노이즈가 메인 스레드를 오염시키지 않는다
4

가비지 컬렉션

쓰레기 청소
주기적으로 실행되는 청소 에이전트가 불필요해진 정보·코드를 정리
실제 사례 — Stripe의 자율 코딩 에이전트 'Minions'는 샌드박스·결정적 게이트·자체 검증 루프로 구성된 하네스 위에서 주당 1,300건 이상의 PR을 사람 리뷰만 거쳐 병합한다. Microsoft Azure SRE Agent는 하네스로 3만 5천 건 이상의 장애를 자율 처리해, 평균 복구 시간을 40.5시간에서 3분으로 줄였다.
→ 시간이 지날수록 하네스는 점점 더 정교해진다
5
Stage 05

루프 엔지니어링

AI 에이전트가 스스로 실행·검증·개선하도록 반복 가능한 피드백 구조를 만드는 방식.

사람의 일회성 지시가 아니라, 계획 → 실행 → 테스트 → 수정의 반복 구조를 만들어 AI 성능을 지속적으로 향상시킨다. 핵심은 AI에게 일을 맡기는 것이 아니라, AI가 스스로 결과를 점검하고 개선하도록 루프를 설계하는 것.

계획Plan
→
실행Build
→
검증Evaluate
→
수정Refine
↻ 반복 (Repeat)
공식화하면: 목표(Goal) → 계획(Plan) → 실행(Act) → 관찰(Observe) → 검증(Check) → 수정(Revise) → 반복(Repeat). "나는 이제 Claude에게 프롬프트를 안 준다. 대신 돌아가는 루프가 있다." — Boris Cherny

메이커 · 체커 패턴

단일 에이전트에게 "혼자 만들고 검사도 해봐"라고 맡기면 스스로에게 관대해져 가짜 성공을 보고하기 쉽다. 초안을 뽑는 메이커 에이전트와 기준으로 날카롭게 검증하는 체커 에이전트를 독립적으로 분리해 병렬로 돌릴 때 결과물의 신뢰도가 올라간다.

현실적인 위험 — 통제되지 않은 루프는 하룻밤 새 억 단위 토큰을 소모하는 비용 폭탄이 되거나, 스스로 만든 결과를 검증 없이 재입력하며 품질이 하향 평준화되는 '모델 붕괴' 리스크로 이어질 수 있다. 루프를 짜기 전 목표·컨텍스트·도구·검증 기준·상태 기억·중단 조건, 이 6가지부터 정의해야 안전하다.
6
Stage 06

그래프 엔지니어링

여러 에이전트의 작업을 노드와 엣지로 그려, 순서·병렬·분기·사람 승인 지점까지 설계하는 방식.

2026년 7월 18일, Peter Steinberger가 "우리 아직 루프 얘기 중인가요, 아니면 벌써 그래프로 넘어갔나요?"라는 글을 올렸고 170만 회 넘게 조회되며 다음 화두를 예고했다. 하나의 에이전트가 도는 반복(루프)만으로 감당이 안 되는 규모의 일을, 여러 전문화된 에이전트로 쪼개 명시적인 흐름으로 연결하는 것이 그래프 엔지니어링이다. 루프가 에이전트의 행동을 프로그래밍한다면, 그래프는 에이전트 조직을 프로그래밍한다.

N

노드 (Node)

일을 하는 단위. 에이전트일 수도, 도구 호출이나 사람의 확인 단계일 수도 있다

E

엣지 (Edge)

노드 사이의 연결선. 앞 노드의 결과물이 뒷 노드의 입력으로 전달된다

C

조건부 엣지

결과에 따라 경로가 갈리는 연결선. "통과면 발행, 실패면 재시도" 같은 분기를 그래프 안에 표현

직렬 체인의 한계

불필요한 줄서기서로 관계없는 작업까지 차례를 기다림
하나가 멈추면 전부 멈춤중간 실패가 뒤 단계 전체를 막음
분기를 넣기 어려움"실패하면 재시도"를 표현하려면 흐름 밖에 코드를 덧대야 함

그래프 구조의 해결

병렬 실행의존 관계 없는 노드는 동시에 실행
분기 내장조건부 엣지로 갈림길을 그래프 안에 포함
부분 재실행체크포인트를 두면 실패한 가지만 다시 실행

대표적인 그래프 패턴

1

파이프라인

Pipeline
조사 → 초안 → 검토 → 발행처럼 순서가 필요한 일을 한 줄로 잇는 기본형
2

팬아웃 / 팬인

Fan-out / Fan-in
독립적인 작업을 여러 노드에 동시에 맡겼다가, 끝나면 종합 노드가 결과를 모으는 형태. 단, 병렬로 묶은 가지끼리는 서로의 결과가 필요 없어야 한다
3

조건 분기

Conditional Branch
결과 평가에 따라 통과·재시도·사람 호출로 경로가 갈리는 형태. 발행 직전에 사람 승인 노드를 넣는 것도 이 패턴
4

피드백 순환

Feedback Loop
작성 노드와 비평 노드가 결과를 주고받는 형태. 무한 반복을 막는 횟수 제한과 함께 사용
두 개의 그래프: 누가 어떤 영역을 담당하는지 정의하는 안정적인 '조직 그래프'와, 일이 진행되며 갈라지고 합쳐지는 동적인 '작업 그래프'가 함께 움직인다 — 조직도는 고정, 작업 흐름은 실시간으로 재구성된다.

대표 도구 (2026.7 기준)

LangGraph그래프 전용 프레임워크. 상태 저장·체크포인트·조건부 엣지 지원 (2025.10 정식 출시)
Microsoft Agent FrameworkAutoGen과 Semantic Kernel 통합. 형식 검증되는 엣지, 슈퍼스텝 병렬 실행 (2026.4 정식 출시)
Strands Agents다른 그래프까지 노드로 넣을 수 있는 패턴 제공. 순환 구조와 실행 횟수 제한 지원
MastraTypeScript 기반 워크플로 프레임워크로 빠르게 성장 중
참고 — 그래프 설계에는 그만큼 비용이 따른다. 모든 노드·엣지·실패 시나리오를 미리 선언해야 하므로, 병렬로 처리할 작업이 실제로 쌓였을 때 도입하는 편이 낫다. 하나의 에이전트와 대화하듯 맡기는 방식이 여전히 유효한 경우도 많다.
